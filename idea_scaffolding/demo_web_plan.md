# 웹서비스 데모 기획

## 1. 데모의 목적

이 데모는 완성된 부동산 플랫폼을 구현하는 것이 아니라, 동업자와 잠재고객에게 다음 핵심 경험을 보여주는 공유용 프로토타입이다.

> 주소를 입력하면 부동산 데이터가 수집되고, 매입가격·임대·리모델링·신축 시나리오를 비교하여 다음 행동을 제안한다.

### 주요 관람자

- 공동창업자 S
- 초기 투자자와 건물 매입 희망자
- 시공사·건축사 등 협업 파트너
- 향후 개발 또는 사업 자문을 제공할 관계자

### 데모에서 확인할 질문

- 고객이 서비스 가치를 1분 안에 이해하는가?
- 어떤 결과 화면에 가장 큰 관심을 보이는가?
- 무료 진단 후 유료 보고서나 상담을 요청하는가?
- S가 실제 영업 과정에서 이 화면을 사용할 수 있는가?

---

## 2. 데모의 핵심 이야기

데모 사용자는 하나의 예시 건물을 검토하는 투자자다.

```text
1. 주소와 희망 매입가격 입력
2. 데이터 수집·분석 과정 확인
3. 핵심 투자 결론 확인
4. 주변 거래와 현재 건물 상태 확인
5. 네 가지 투자 시나리오 비교
6. 위험과 추가 실사 항목 확인
7. 전문가 보고서 또는 현장답사 신청
```

데모는 기능의 수보다 이 흐름이 자연스럽게 이어지는 것이 중요하다.

---

## 3. 화면 구성

## 3.1 시작 화면

### 목적

서비스가 무엇을 해주는지 설명하고 사용자가 바로 주소를 입력하도록 한다.

### 주요 요소

- 한 문장 가치 제안
- 주소 입력
- 희망 매입가격 입력
- 투자 목적 선택
- `무료 분석 시작` 버튼
- 미리 준비된 예시 건물 선택
- 분석 항목과 전문가 검토 방식에 대한 짧은 설명

### 권장 문구

> 이 건물, 얼마에 사야 수익이 날까요?
>
> 주소와 매입 조건을 입력하면 가격·임대·리모델링·개발 가능성을 비교해 드립니다.

데모에서는 실제 주소 검색 API 없이 미리 준비한 예시 주소를 자동완성 형태로 제공해도 된다.

---

## 3.2 분석 진행 화면

### 목적

AI가 막연히 답을 생성하는 것이 아니라 여러 근거를 수집하고 계산한다는 신뢰를 만든다.

### 진행 단계

1. 주소와 필지 확인
2. 토지·건축물 정보 조회
3. 주변 실거래 비교
4. 임대수익 분석
5. 리모델링·신축 시나리오 계산
6. 전문가 확인 항목 정리

데모에서는 2~4초 동안 단계가 순차적으로 완료되는 연출을 사용한다. 실제 분석이 아니라는 점은 페이지 하단에 표시한다.

---

## 3.3 결과 요약 화면

사용자가 처음 보게 되는 핵심 화면이다.

### 상단 결론 카드

- 검토 의견: 조건부 매입 검토
- 권장 매입가격
- 협상 중단 가격
- 예상 자기자본
- 기준 시나리오 IRR
- 핵심 위험
- 다음 행동

### 자산 요약

- 토지면적과 연면적
- 건축연도와 주용도
- 건폐율·용적률
- 현재 임대수익률
- 공실 현황
- 데이터 기준일

### 화면 원칙

- 종합점수보다 행동 가능한 결론을 우선한다.
- 금액은 억 원, 면적은 ㎡와 평을 함께 표시한다.
- 추정값과 확인값을 시각적으로 구분한다.
- 모든 주요 결과에 출처 또는 계산 기준을 연결한다.

---

## 3.4 주변 거래 화면

### 주요 요소

- 대상 건물과 비교 거래 위치를 표시한 지도
- 최근 거래 사례 목록
- 거래시점·거리·용도·연면적 차이
- 토지 평당가격 및 연면적 평당가격
- 비교 대상으로 사용한 이유
- 비교에서 제외한 거래와 제외 사유

초기 데모에서는 예시 거래 5건을 사용한다. 실제 공공데이터 API 연결은 상용 MVP 단계에서 진행한다.

---

## 3.5 시나리오 비교 화면

### 비교 대상

1. 현 상태 매입·보유
2. 공실 해소와 임대 개선
3. 리모델링 후 임대·매각
4. 신축 상세검토

### 공통 비교 항목

- 총투자비
- 필요 자기자본
- 안정화 순영업소득
- 예상 보유기간
- 예상 매각가치
- 자기자본 수익률
- IRR 범위
- 주요 위험

### 데모 인터랙션

- 매입가격 슬라이더
- 대출비율 선택
- 금리 변경
- 공실률 변경
- 리모델링 비용 변경
- 입력 변경에 따른 수익률과 결론 갱신

이 화면이 데모의 핵심이다. 단순 보고서보다 “조건을 바꾸어 의사결정을 시험할 수 있다”는 제품 가치를 보여준다.

---

## 3.6 위험 및 실사 화면

### 위험 분류

- 데이터 미확인
- 현장 확인 필요
- 건축사 확인 필요
- 법률·권리 확인 필요
- 세무 확인 필요

### 예시 항목

- 불법 증축 여부
- 임대차계약서와 실제 점유 현황
- 위반건축물 및 주차 요건
- 리모델링 공사 범위
- 대출 조건과 금리 변동

각 항목은 `확인 완료`, `추정`, `미확인` 상태를 갖는다.

---

## 3.7 전환 화면

### 주요 행동

- 전문가 검토 보고서 신청
- S와 현장답사 요청
- PDF 샘플 보기
- 링크 복사 또는 공유

데모에서는 실제 결제 대신 상담 신청 폼 또는 이메일 연결만 제공한다.

## 4. 정보 구조

```text
/
├─ 시작 및 주소 입력
├─ 분석 진행
└─ /report/demo-building
   ├─ 요약
   ├─ 주변 거래
   ├─ 시나리오
   ├─ 위험 및 실사
   └─ 전문가 상담
```

GitHub Pages 배포를 고려하여 정적 단일 페이지 애플리케이션으로 구성한다. URL 경로가 필요한 경우 새로고침 시 오류가 나지 않도록 해시 라우팅 또는 Pages용 라우팅 설정을 사용한다.

## 5. 데모 데이터

### 예시 자산

실제 고객정보가 아닌 익명화 또는 가상 건물 한 건을 사용한다.

- 서울 내 중소형 노후 근생 건물
- 매입가격 70억 원대
- 일부 공실 존재
- 현행 용적률에 여유
- 리모델링과 임대 개선을 비교할 수 있는 조건

### 필요한 데이터 묶음

- 토지·건축물 기본정보
- 주변 거래 5건
- 층별 임대차 현황
- 대출 조건
- 리모델링 비용 가정
- 매각가치 가정
- 위험 및 실사 항목

모든 화면에 `데모용 예시 데이터`임을 표시한다. 실제 공공데이터처럼 보이게 하되, 존재하지 않는 출처를 만들지 않는다.

## 6. 디자인 방향

### 제품 인상

- 신뢰할 수 있는 투자심사 자료
- 고가 부동산을 다루는 전문성
- 복잡한 정보를 빠르게 이해할 수 있는 명료함

### 화면 원칙

- 화려한 AI 이미지보다 숫자와 근거를 중심으로 구성
- 흰색 또는 밝은 중립 배경
- 진한 남색·차콜 계열을 기본색으로 사용
- 상승 기회, 주의, 위험 상태의 색을 일관되게 구분
- 보고서와 대시보드의 중간 형태
- 모바일에서도 핵심 결론과 시나리오 비교가 가능하도록 반응형 구성

실제 구현 전에는 동일한 화면 구성을 바탕으로 세 가지 시각 방향을 비교하고 하나를 선택한다.

## 7. 데모 기술 구성

### 권장 스택

- React + TypeScript
- Vite
- 반응형 CSS 또는 Tailwind CSS
- 차트 라이브러리
- 지도는 키 없이 사용할 수 있는 데모 방식을 우선 검토
- 정적 JSON 기반 예시 데이터
- GitHub Actions + GitHub Pages

### 데모에서 서버를 두지 않는 이유

- 공유와 실행이 단순하다.
- API 키와 개인정보를 저장하지 않는다.
- GitHub Pages만으로 바로 확인할 수 있다.
- 제품 흐름과 고객 반응을 먼저 검증할 수 있다.

### 상용 MVP로 전환할 때 추가할 항목

- 사용자 인증과 권한
- PostgreSQL + PostGIS
- 공공데이터 수집 작업
- 보고서 저장과 버전 관리
- PDF 생성
- 결제 및 상담 CRM
- 원본 자료 암호화와 접근기록
- 전문가 승인 워크플로

## 8. 에이전트 기반 제작 계획

K가 최종 구조와 품질을 책임지고, 독립적인 작업은 에이전트에 병렬로 배분한다.

| 작업 흐름 | 담당 |
|---|---|
| 제품 구조와 데이터 계약 | K |
| 화면 카피와 예시 시나리오 | S + K |
| 프런트엔드 화면 구현 | 구현 에이전트 |
| 예시 데이터와 계산 로직 | 데이터·분석 에이전트 |
| 반응형·접근성·오류 검토 | QA 에이전트 |
| 최종 화면과 수치 검수 | S + K |

동일 파일을 여러 에이전트가 동시에 수정하지 않도록 화면 또는 기능 단위로 작업 범위를 나눈다.

---

## 9. 데모 제작 일정

프런티어 코딩 에이전트를 사용하고, 실제 API와 백엔드를 제외한 경우의 일정이다.

| 일정 | 결과 |
|---|---|
| 1일차 | 핵심 사용자 흐름, 예시 건물, 화면 문구 확정 |
| 2일차 | 세 가지 시각 방향 비교 및 하나 선택 |
| 3~4일차 | 시작·분석·결과·시나리오 화면 구현 |
| 5일차 | 반응형, 오류 상태, 공유 흐름 검수 |
| 6일차 | GitHub Pages 배포 및 동업자 피드백 수집 |

공유 가능한 데모는 약 4~6작업일을 목표로 한다. 실제 데이터 API를 연결하는 순간부터는 데모가 아니라 MVP 개발 일정으로 관리한다.

---

## 10. 완료 기준

- 처음 보는 사람이 1분 안에 서비스 목적을 설명할 수 있다.
- 주소 입력부터 결과 확인까지 막힘 없이 진행된다.
- 결과 화면에 권장가격·자기자본·수익률·위험·다음 행동이 보인다.
- 매입가격과 금융 조건을 바꾸면 시나리오 결과가 갱신된다.
- 모바일과 데스크톱에서 핵심 내용이 잘린 부분 없이 표시된다.
- 모든 수치가 데모 데이터임을 명확히 알 수 있다.
- API 키나 개인정보 없이 GitHub Pages에서 작동한다.
- S가 고객에게 링크를 보내고 상담을 이어갈 수 있다.

---

## 11. 데모 이후 판단

동업자와 잠재고객에게 보여준 뒤 다음 질문으로 MVP 범위를 결정한다.

- 결과 요약과 시나리오 중 어느 화면이 더 설득력 있었는가?
- 고객이 자신의 실제 주소를 입력하고 싶어 했는가?
- 유료 보고서를 요청했는가?
- S가 영업 도구로 사용할 의사가 있는가?
- 실제 API 연결이 가장 필요한 데이터는 무엇이었는가?

이 결과를 바탕으로 상용 MVP의 데이터 연결 순서와 첫 유료 상품을 확정한다.
